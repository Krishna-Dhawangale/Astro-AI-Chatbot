1. EXECUTIVE SUMMARY & OBJECTIVE
--------------------------------------------------------------------------------
This plan addresses the critical intent misclassification issue (e.g. "Tell me my 
current Dasha and how my career will be" incorrectly predicting intent="health_period" 
@ 13% confidence) and establishes a permanent 10-phase validation roadmap for 
routing, API normalization, reasoning engine, local answer generation, Gemini fallback,
and multi-domain question handling.

STRICT CONSTRAINTS ENFORCED:
- DO NOT retrain, overwrite, or delete any model artifacts (.pkl files).
- DO NOT alter the Stage 8 reasoning engine rules or normalize.py logic.
- DO NOT modify production code without presenting exact file diff proposals 
  and waiting for explicit user approval.
- DO NOT alter existing API response contracts or frontend interfaces.


2. DIAGNOSIS OF INTENT CLASSIFIER ISSUE
--------------------------------------------------------------------------------
- Symptom: "Tell me my current Dasha and how my career will be." predicts intent="health_period" (Conf: 0.130).
- Root Cause: intent_model.pkl is a raw TF-IDF classifier. For multi-part queries 
  combining Dasha inquiry + Career inquiry, model confidence drops to ~13% and defaults 
  to "health_period".
- Proposed Fix in backend/router/intent.py:
  1. Implement predict_intent_with_confidence(question) returning label, confidence, 
     and top probability distribution.
  2. Implement a multi-intent & low-confidence pattern overlay:
     - When confidence is low (< 0.50) or multi-domain markers are present:
       * Dasha + Domain query (e.g. "dasha" + "career" / "job") -> intent = "multi_domain"
       * Single Dasha query ("what is my mahadasha") -> intent = "dasha"
       * Promotion query ("promoted", "promotion") -> intent = "career_promotion"
       * Marriage timing ("when will i get married") -> intent = "marriage_timing"
       * Income query ("income increase") -> intent = "income"
       * Definition query ("what is a nakshatra") -> intent = "definition"


3. PHASES 4–10 VALIDATION ROADMAP
--------------------------------------------------------------------------------

PHASE 4: Validate Complete ML Router
- Test the full routing pipeline: Question -> Normalization -> Domain -> Complexity -> Intent -> Route Decision.
- Ensure "Will my career improve during my current Dasha?" resolves to:
  Domain: career | Complexity: needs_chart | Intent: career_promotion/career_general | Route: astrology
- Ensure "Tell me my current Dasha and how my career will be." resolves to:
  Domain: other/career | Complexity: needs_chart | Intent: multi_domain | Route: astrology

PHASE 5: Validate API + normalize.py Boundary
- Verify that FreeAstrologyAPI / Prokerala responses pass through normalize.py to 
  produce InternalAstroSchema without local recalculation of planetary positions, 
  Ascendant, Moon sign, Nakshatra, Dasha, Antardasha, or transits.

PHASE 6: Validate Reasoning Engine (Stage 8)
- Verify that Stage 8 produces usable evidence for the exact intent selected by ML Router 
  for domain queries (career, marriage, finance, education, property).

PHASE 7: Verify Local Answer Layer
- Ensure that when Stage 8 evidence exists for the intent, main.py constructs a local 
  deterministic answer labeled "(Deterministic Reasoning)" without calling Gemini.

PHASE 8: Test Gemini Fallback & Zero-Call Verification
- Mock Gemini client during test suite execution.
- Assert gemini_calls == 0 for all locally answerable questions (FAQ, Dasha API, Stage 8 Reasoning).
- Assert gemini_calls == 1 for unresolved out-of-scope questions.

PHASE 9: Multi-Domain Question Handling
- Test queries combining Dasha + Domain (e.g. "Tell me my current Dasha and how my career will be."):
  1. Dasha portion -> Deterministic Dasha API answer
  2. Career portion -> Stage 8 Reasoning Engine local answer
  3. Combined -> Merged multi-domain deterministic response (Zero Gemini calls).

PHASE 10: End-to-End Acceptance Test Suite
- Permanent test suite in run_acceptance_tests.py covering 12 categories:
  A. FAQ
  B. Domain classification
  C. Complexity classification
  D. Intent classification
  E. Multi-domain resolution
  F. API retrieval
  G. Normalization boundary
  H. Reasoning engine
  I. Local answer formatting
  J. Gemini zero-call verification
  K. Response schema contract
  L. Frontend compatibility
